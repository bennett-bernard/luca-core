The recommendation

Persistence first, export second

A durable SQL adapter validates the architecture established in Milestone 1. CSV then becomes a clean output adapter over a stable posting projection.

→

Start with one vertical SQLite workflow

Migrate an empty database, persist a balanced entry, close the process, reopen it, retrieve the same domain model, and export its postings. Verify PostgreSQL parity while the schema is still small.

01 / PROVE

Validate the repository boundary

Private ORM rows and explicit mappers must produce the same validated Pydantic records as the in-memory adapter.

02 / PROTECT

Make workflows atomic

A unit of work makes entry creation and deletion-plus-audit succeed or roll back as one transaction.

03 / PROJECT

Flatten postings for data out

Resolve account and journal display details into a read-only posting row, then write deterministic CSV without changing journal-line storage.

Watch points

Highest-impact risks

Decimal rounding

Gate the schema on adversarial exact round-trip tests for both databases.

Historical deletion

Use restrictive foreign keys and lifecycle-aware services.

Unaudited deletion

Share one unit of work and transaction between record and audit writes.

ORM leakage

Return reconstructed Pydantic models that survive session closure.

Backend drift

Run migration and repository contracts against real PostgreSQL early.

CSV schema drift

Name the initial posting export format and version incompatible changes.
